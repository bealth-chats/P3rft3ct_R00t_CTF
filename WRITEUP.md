# CTF Writeup: The Silent Vault

## Challenge Description
The challenge provides a contract address on the Sepolia Testnet (`0xD702054866DEA4840ab36D4f222C757a3349c422`) and the bytecode instructions. The goal is to find the `msg.value` that opens the vault.

## Analysis

### 1. Fetching Bytecode
First, we fetched the runtime bytecode of the contract from the Sepolia network.
```bash
curl ... https://ethereum-sepolia-rpc.publicnode.com
```

### 2. Disassembling
We disassembled the bytecode to understand the logic. The relevant part of the code is:

```assembly
0041: JUMPDEST
0042: PUSH1 0x20
0044: CALLDATASIZE
0045: EQ
0046: PUSH1 0x4c
0048: JUMPI
...
004c: JUMPDEST
004d: PUSH30 0x346e346c797a316e675f62797433633064335f6c316b335f345f70723000
006c: PUSH0
006d: MSTORE
006e: PUSH1 0x1e
0070: PUSH0
0071: SHA3
0072: CALLVALUE
0073: DUP2
0074: SLOAD
0075: EQ
0076: PUSH1 0x7c
0078: JUMPI
```

**Logic Breakdown:**
1. **Check Calldata Size**: The code requires `msg.data` length to be exactly 32 bytes (`0x20`). If not, it reverts.
2. **Push Secret String**: It pushes a 30-byte value onto the stack:
   `0x346e346c797a316e675f62797433633064335f6c316b335f345f70723000`
   Decoding this hex string gives: `4n4lyz1ng_byt3c0d3_l1k3_4_pr0` followed by a null byte `\x00` (since `30` is '0', `00` is null).
3. **Store in Memory**: It executes `MSTORE(0, value)`.
   - `PUSH30` pushes the value as a `uint256`, effectively left-padding it with zeros.
   - Stack: `0x0000346e...`
   - Memory at 0: `00 00 34 6e ... 30 00`.
4. **Calculate Hash**: It executes `SHA3(0, 30)`. This hashes the first 30 bytes of memory:
   - Bytes: `00 00 34 6e ... 72 30` (Wait, it misses the last `00`).
5. **Check Storage**: It loads the value from storage at the calculated hash and compares it with `msg.value`.

### 3. finding the Flag
We calculated the storage slot generated by the code's logic:
`keccak256(0000346e...)` -> `0xb77ed8df0c9bccb800f70c61b747d97ab9741319cd6f0b3b5762e91438d34a44`.
Checking this storage slot on Sepolia returned `0`.

This suggests that `msg.value` must be `0` to satisfy the condition `0 == 0`.

However, we suspected that the intended logic was to hash the string itself.
We calculated the hash of the clean string `4n4lyz1ng_byt3c0d3_l1k3_4_pr0`:
`keccak256("4n4lyz1ng_byt3c0d3_l1k3_4_pr0")` -> `0x47d34f5b68ee0923afd1e5cdc53211fd27be3332134da08878f3e53fac89721b`.

Checking this storage slot returned a non-zero value:
`0x0000000000000000000000000000000000000000000000000000000406de73ad7a8137c0`

Decimal value: `4642542409869375424`.
(This is approximately 4.64 ETH).

### Conclusion
The contract contains a bug in how it generates the storage key from the string (due to integer padding and memory alignment). As a result, the runtime code checks against an empty storage slot (requiring `msg.value = 0`). However, the secret was correctly stored at the hash of the string during deployment.

Given the nature of the challenge, the flag is the intended secret value.

**Flag:** `r00t{4642542409869375424}`
